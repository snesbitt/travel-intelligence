Field note

An early version of the pricing model priced every Business class round-trip near the same figure regardless of route or carrier — a rounding floor was silently overriding the seeded variation underneath it. Step 03 exists because a recommendation is only as trustworthy as the numbers feeding it, and that only surfaced by actually running the engine end-to-end and reading the raw output, not by reasoning about the code in the abstract.

02Reference ranges, not a live search — and labeled as such

Every fare shown is generated from a per-cabin base price plus seeded variation for stops, fare tier, and date flexibility — a planning model, not a fetched quote. Every mileage figure comes from hand-maintained round-trip ranges by cabin (e.g. Business: roughly 115,000–320,000 miles plus taxes/fees), the same kind of commonly-cited planning range a knowledgeable advisor would quote from memory before pulling up live availability. Upgrade-friendliness scores are a general reputation judgment per carrier, not a live seat-map read. Nothing here is presented as a live quote — the sync banner on the homepage says so directly, and this page says exactly which numbers are computed vs. referenced.

03Six dimensions, weighted by your ranking — never a single variable

Every candidate itinerary is scored 0–100 on Cost, Comfort, Upgrade Potential, Award Value, Flexibility, and Risk. Your ranked priority list (Cheapest through Best Overall Experience) maps onto those six dimensions with a fixed weighting table, and a rank-1 priority pulls more weight than a rank-7 one. The final weighted score is a straightforward dot product — shown on the results page as an explicit percentage per dimension, so the trade-off behind the recommendation is never hidden behind a single black-box number.

Always shown

The exact weight (as a %) each of the six dimensions received, computed live from your priority ranking — not a fixed default.

Never done

Optimizing for price alone. A cheaper itinerary that scores meaningfully worse on your higher-ranked priorities will not out-score the better-rounded one.

04A model, not a live connection

As with the other two systems in this portfolio, this one is explicit about what's real. It doesn't connect to Google Flights, ITA Matrix, seats.aero, or any airline system — every number is either computed from your inputs in real time or drawn from a hand-maintained reference range. Re-running the same inputs reproduces the same result, the same way a tested pure function would: this is deterministic by design, not random.

05Static deploy today, GitHub + Netlify Functions next

This build ships as static HTML/CSS/JS to Netlify — no backend required for a scoring engine that runs entirely in the browser. A GitHub repo mirrors the other two sites' governance model (push to main, Netlify auto-deploys), and is the on-ramp to Phase 2's live data functions once those are approved and built.

06What's still manual — and what's still missing

Live fare and award data is the biggest gap: everything you see today is a documented model, not a search result, and that gap is the whole of Phase 2. Domain registration (matching vinylscout.org / thefitnesslog.org / streamingscout.org) hasn't happened — authorization precedes any expenditure, so that step waits on Susan's explicit go-ahead the same way it did for the other two sites. There's also no saved-preference memory yet: every session starts from the same defaults rather than remembering a prior trip's inputs.

What this took to learn

A recommendation is only as honest as the labels on its numbers — presenting a reference range as if it were a live quote would be worse than not building the feature at all.

Authorization precedes any expenditure. A domain name, a paid API key, or any real spend is a decision left to Susan, never delegated.
