Field note

An early version of the pricing model priced nearly every Business class round-trip at the same figure, regardless of route or carrier: a rounding floor was overriding the variation built into the model. Step 03 exists because a recommendation is only as trustworthy as the numbers behind it. The error was found by running the engine end-to-end and reading the output, not by reviewing the code alone.

02Reference ranges, not a live search — and labeled as such

Fares now have two modes, and the banner on the homepage always states which one you're in. With the SerpApi credential configured, every run searches real Google Flights fares through the site's own backend and scores them with the engine below — real prices, same framework. Without it, fares come from the documented model: a per-cabin base price scaled by the route's actual great-circle distance (from a hand-maintained city coordinates table), plus variation for stops, fare tier, and date flexibility. Mileage figures in both modes are hand-maintained, distance-scaled planning ranges — award availability is not searched yet. Upgrade-friendliness scores are a general reputation judgment per carrier, not a live seat map.

One class of numbers is different, and labeled differently: the Points Intelligence panel. Point valuations (which airline's miles are worth the most in cents per point) and active transfer bonuses are real published figures from The Points Guy's monthly valuations, hand-copied with their date shown in the UI, and refreshed by hand each month. They're facts with a timestamp, not a model output — and not a live feed either, which is why the as-of date is always displayed next to them.

03Six dimensions, weighted by your ranking — never a single variable

Every candidate itinerary is scored 0 to 100 on Cost, Comfort, Upgrade Potential, Award Value, Flexibility, and Risk. Your ranked priority list, from Cheapest to Best Overall Experience, maps onto those six dimensions through a fixed weighting table: a rank-1 priority carries more weight than a rank-7 one. The final score is a weighted sum, shown on the results page as an explicit percentage per dimension, so the reasoning behind the recommendation is never reduced to a single number.

Always shown

The exact weight (as a %) each of the six dimensions received, computed live from your priority ranking — not a fixed default.

Never done

Optimizing for price alone. A cheaper itinerary that scores meaningfully worse on your higher-ranked priorities will not out-score the better-rounded one.

04One class of numbers is still a model

As with the other systems in this portfolio, this one states plainly what's real. Fares are live Google Flights data when the backend is connected (the banner says which mode you're in). Mileage and award figures are NOT live — they're hand-maintained, distance-scaled planning ranges, because award availability isn't searched yet — and the scoring model itself is deterministic: the same inputs and the same fares produce the same result, by design, not randomized.

05Static deploy today, GitHub + Netlify Functions next

This build ships as static HTML, CSS, and JavaScript to Netlify. No backend is required for a scoring engine that runs entirely in the browser. A GitHub repository will mirror the other sites' deployment model — push to main, Netlify deploys automatically — and becomes the foundation for Phase 2's live data functions once those are approved and built.

06What's still manual — and what's still missing

Award-space search is the largest remaining data gap — mileage figures are planning ranges, never availability checks. The watcher now does the daily fare-watching automatically (capped at three trips because each check spends one metered search — raising that cap, or adding email/push alerts, needs a new credential or quota decision and therefore Susan's explicit approval, the same rule as all real spend). Saved memory covers the wallet and watched trips; other inputs still reset each session. The TPG valuation and transfer-bonus tables remain a manual monthly refresh — copied by hand with their date shown, so a stale month is visible rather than silent.

What this took to learn

A recommendation is only as trustworthy as the labels on its numbers. Presenting a reference range as a live quote would be worse than not building the feature at all.

Authorization precedes any expenditure. A domain name, a paid API key, or any real spend is a decision left to Susan, never delegated.
