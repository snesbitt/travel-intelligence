01Tools & mode

Built in Cowork, by design. The Input Card, scoring engine, and every output section run as plain JavaScript in your browser. Two things leave it, both stated plainly: a fare search sends the route, dates, cabin, and traveler count to the site's own /api/fares function, and watching a trip stores that route server-side so the daily check can run. Your wallet — cards and balances — never leaves the browser.

02Reference ranges, not a live search — and labeled as such

Fares have exactly one mode: real. Every run pulls live Google Flights fares through the site's own backend, merges in any fares scanned from your own Kayak or Booking searches (each carries a labeled source pill), and scores them with the engine below. If nothing real comes back, the site says so and shows no figures at all — the old synthetic fallback model was deleted in July 2026, on the principle that a plausible invented number is worse than an honest empty state. Flight-time estimates for offers that omit a duration come from real great-circle geometry (a hand-maintained city coordinates table). Mileage figures are hand-maintained, distance-scaled planning ranges — award availability is not searched yet. Upgrade-friendliness scores are a general reputation judgment per carrier, not a live seat map.

One class of numbers is different, and labeled differently: the Points Intelligence panel. Point valuations (which airline's miles are worth the most in cents per point) and active transfer bonuses are real published figures from The Points Guy's monthly valuations, hand-copied with their date shown in the UI, and refreshed by hand each month. They're facts with a timestamp, not a model output — and not a live feed either, which is why the as-of date is always displayed next to them.

03Seven dimensions, weighted by your ranking — never a single variable

Every candidate itinerary is scored 0 to 100 on Cost, Comfort, Upgrade Potential, Award Value, Flexibility, Risk, and Time. Your ranked priority list, from Cheapest to Best Overall Experience, maps onto those seven dimensions through a fixed weighting table: a rank-1 priority carries more weight than a rank-7 one. The final score is a weighted sum, shown on the results page as an explicit percentage per dimension, so the reasoning behind the recommendation is never reduced to a single number. Time was added 2026-07-25, after Fastest and Cheapest returned the same pick on a route where every offer had one stop — Risk only scored stop count, so there was nothing left for "fastest" to actually rank by.

Always shown

The exact weight (as a %) each of the seven dimensions received, computed live from your priority ranking — not a fixed default.

Never done

Optimizing for price alone. A cheaper itinerary that scores meaningfully worse on your higher-ranked priorities will not out-score the better-rounded one.

The actual math, in full: each of the 7 priority lenses (Cheapest, Best Value, Fastest, Most Comfortable, Best Upgrade Opportunity, Best Use of Miles, Best Overall Experience) has its own fixed weight per dimension, hand-tuned in app.js. If you rank more than one priority, a rank-1 pick's vector counts more than a rank-2 pick's, by this formula:

rankWeight   = (totalPriorities + 1 − rank) / totalPriorities
dimWeight[d] = Σ (priorityVector[priority][d] × rankWeight[priority])
               — then normalized so all 7 weights sum to 1
score        = Σ (dimensionScore[d] × dimWeight[d])  for d in the 7 dimensions

For example, under "Best Overall Experience" — the default lens most results are viewed through — the fixed vector is Cost 1.4, Comfort 0.5, Upgrade 0.4, Award 0.3, Flexibility 0.3, Risk 0.3, Time 0.2. Cost was raised from 0.3 to 1.4 on 2026-07-19, a direct, documented judgment call: an earlier version had a $2,400 nonstop beating a $1,300 one-stop under "Best Overall," which didn't hold up as a real recommendation. The new weight was tuned against that exact case and pinned by a regression test, so it can't silently drift back.

04One class of numbers is still a model

This site states plainly what's real. Fare prices are always real — the live Google Flights feed and/or your own Kayak/Booking scans, as labeled — or absent. Mileage and award figures are NOT live: they're hand-maintained, distance-scaled planning ranges, because award availability isn't searched yet. And the scoring itself is deterministic: the same inputs and the same fares produce the same result, by design, not randomized.

05Push to main, Netlify deploys — three small Functions, nothing more

The code lives in an ordinary GitHub repository, and every push to the main version auto-publishes to the live site with no manual step. The backend is deliberately tiny: three small, single-purpose pieces of code (fares — the live search, watch — the watched-trips list, watch-check — the daily automatic re-check) and nothing else. No extra framework, no build step, no database beyond one simple storage service. Radical simplicity is the standing rule here: a feature that needs more infrastructure has to earn it.

06What's still manual — and what's still missing

Award-space search is the largest remaining data gap — mileage figures are planning ranges, never availability checks. The watcher now does the daily fare-watching automatically (capped at three trips because each check spends one metered search — raising that cap, or adding email/push alerts, needs a new credential or quota decision and therefore Susan's explicit approval, the same rule as all real spend). Saved memory covers the wallet and watched trips; other inputs still reset each session. The TPG valuation and transfer-bonus tables remain a manual monthly refresh — copied by hand with their date shown, so a stale month is visible rather than silent.
